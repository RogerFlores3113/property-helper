<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → Frontend Server | Session cookie travels on every request; middleware refresh validates it |
| Browser tab → Layout SSR read | Server Component reads getUser() result; cookie cannot be forged client-side because HttpOnly |
| Sign-out click → Supabase Auth | signOut() revokes the refresh token server-side AND clears local cookies |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-02 | Tampering | Session cookie theft / fixation | mitigate | @supabase/ssr writes HttpOnly cookies by default — XSS cannot read them. Layout uses getUser() (server-validated) NOT getSession() (cookie-only) for the auth branch. Acceptance criterion enforces getUser in source. |
| T-06-04 | Elevation of Privilege | Auth bypass via stale layout render after sign-out | mitigate | SignOutButton calls BOTH router.push('/') AND router.refresh() per Pitfall 7. Without refresh, the Server Component layout would show the cached user email until next navigation, leaking the impression of an active session. Acceptance criterion enforces both calls in source. |
| T-06-08 | Information Disclosure | Long email overflowing header layout, leaking adjacent UI | accept | UI-SPEC mandates `truncate max-w-[200px]`. CSS truncation is enforced by acceptance criterion grep. Layout adjacency not security-critical for v1. |
| T-06-09 | Spoofing | Fake "you're signed in as X" UI on first paint | mitigate | The auth state is read server-side in the layout via getUser() (which validates against Supabase), not from a client-side cookie scrape. The first paint reflects the real session. |
</threat_model>
