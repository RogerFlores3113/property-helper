<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Email inbox → Browser | Magic-link URL travels through email — an attacker who reads the inbox can use the link |
| Browser → /auth/callback | Untrusted query string (`code`, `next`) crosses here |
| Frontend Server → Supabase Auth | exchangeCodeForSession validates the code's signature server-side |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Spoofing | Magic link token interception | mitigate | PKCE: signInWithOtp from the browser sets a code_verifier cookie before redirecting to email; only the same browser can complete exchangeCodeForSession. The "open it in this same browser" copy in /login is a user-facing reinforcement of this contract (Pitfall 6). Codes are single-use and expire in 5 min (Supabase-enforced — accept this as the upstream control). |
| T-06-03 | Tampering | Open redirect via `next` query param on /auth/callback | mitigate | Route handler validates `next` starts with `/`, does NOT start with `//`, and does NOT contain `://` before using it in the redirect URL. Failing values default to `/`. This is defensive: Phase 6 never puts a user-controlled `next` into the magic link, but a future bug or copy-paste could. Acceptance criterion enforces the predicate is present in source. |
| T-06-06 | Information Disclosure | Logging the single-use code or session token | mitigate | Route handler does NOT log the raw `code`. signInWithOtp errors are not surfaced verbatim to the user (canned UI-SPEC copy is shown instead of error.message) — prevents leaking internal Supabase error structure. |
| T-06-07 | Spoofing | Phishing via misdirected magic link | accept | emailRedirectTo is fixed to `${NEXT_PUBLIC_SITE_URL}/auth/callback`, and the Supabase dashboard whitelist is the upstream control. v1 friends-and-family scope; no further mitigation. |
</threat_model>
